# NU40 질의 수신 누락 측정 — 2026-10-10

질의 누락은 Drone의 HMAC 검증보다 앞선 BLE 수신 단계로 좁혀졌습니다. 현재 유력한 후보는 **Reader의 200ms 질의 광고 동안 BLE 확장 광고 전체를 수신하지 못하는 현상**입니다. NU40 스캔 간격도 영향을 줄 가능성이 있지만, 10ms 반복 측정에서도 누락이 재발해 단독 원인으로 확정할 수 없습니다. 응답 방향의 손실도 별도로 관찰됐습니다. 특정 채널의 간섭이나 SoftDevice 내부 스케줄링 중 어느 것이 근본 원인인지는 이 로그만으로 확정할 수 없습니다.

## 조건과 방법

- Reader: ESP32-C3, Arduino-ESP32 3.3.12, NimBLE-Arduino 2.5.0.
- Drone: NU40DK nRF52840, NUBoards 1.0.2, S140 6.1.1 API.
- 양쪽 1M PHY, passive scan, 연결 없는 확장 광고, 광고 간격 50ms, 메시지 38바이트/광고 데이터 45바이트, Drone 응답 광고 600ms.
- 보드 위치·방향·USB 연결은 바꾸지 않았다고 사용자 확인을 받았습니다.
- GUI의 기존 QUERY API로 매번 새 request_id/nonce를 사용했습니다. 약 3.4초 간격, 배치당 12회. 각 질의 후에만 Drone STATUS를 요청해 누적 수신 카운터를 기록했습니다. 자동 RF 재질의는 없습니다.
- Reader TX_CHALLENGE의 nonce와 Drone RX_CHALLENGE/TX_RESPONSE의 nonce를 대조했습니다. 같은 광고의 중복 수신은 질의 성공 수를 늘리지 않습니다.
- 시험 사이 업로드로 보드를 재부팅했습니다. 최초 100ms 복귀 업로드 후 USB STATUS 무응답이 있었으며, 같은 바이너리 재업로드 후 연결을 확인했습니다. 이 연결 확인 질의는 아래 반복 측정에 포함하지 않았습니다.

100ms와 10ms 비교 바이너리의 실제 코드 데이터 차이는 스캔 interval/window에 해당하는 두 바이트뿐이었습니다. Reader 광고 시간 비교 때에는 Drone 바이너리를 바꾸지 않았습니다.

- Drone이 수신한 해당 nonce는 모두 인증을 통과했고 응답 광고를 시작했습니다. 수신 콜백 시각부터 응답 광고 시작까지 로그상 0~1ms였습니다. 키/ID/HMAC 오류, 큐 만료, 큐 오버플로, RADIO_ERROR는 관찰되지 않았습니다.
- 질의를 놓친 구간에도 다른 BLE 광고의 `reports`는 계속 증가했습니다. 스캐너 전체가 멈춘 상황은 관찰되지 않았습니다.
- `resume_errors`, `last_resume_error`, `missed`, `truncated`는 진단 배치에서 모두 0이었습니다. 스택이 보고하기 전에 완전히 놓친 광고까지 이 카운터에 잡히는 것은 아닙니다. 따라서 0을 무선 손실 부재의 증거로 해석할 수 없습니다.
- Drone이 질의를 인증하고 TX_RESPONSE/BROADCAST_STARTED를 기록했는데 Reader가 NO_RESPONSE가 된 경우도 있습니다. 따라서 모든 UNKNOWN을 Drone 질의 수신 실패로 볼 수 없습니다.
- 100ms 진단 두 배치는 수신 4/12와 10/12, 10ms 두 배치는 12/12와 8/12로 편차가 컸습니다. 수신된 패킷의 마지막 RSSI도 약 -78~-55dBm으로 달라졌습니다. 위치가 고정되어도 무선 환경의 변동과 채널별 차이를 통제한 실험은 아니므로, 10ms 설정의 개선을 일반적인 무손실 보장으로 해석하지 않습니다.

## 코드 확인

`firmware/iff/src/FofBoard.h`의 NU40 콜백은 COMPLETE 보고에서 메시지를 복사하고, MORE_DATA를 제외한 보고 뒤 `sd_ble_gap_scan_start(nullptr, &scanBuffer_)`로 재개합니다. 설치된 S140 API의 재개 규칙과 일치합니다. 255바이트 수신 버퍼와 광고 데이터 버퍼의 수명도 유지됩니다.

설치된 Bluefruit 코어는 내장 Scanner 이벤트 핸들러를 사용자 콜백보다 먼저 실행합니다. 기본 필터/콜백 설정에서는 내장 Scanner가 먼저 resume하는 경로가 확인되지 않았습니다. 단순한 이중 재개 충돌을 원인으로 판단할 근거는 없습니다.

NU40의 `micros()`는 DWT가 꺼져 있으면 RTOS tick으로 동작합니다. `max_handler_us=0`은 1ms 미만 처리도 포함하므로 정확한 마이크로초 지연으로 보지 않습니다.

## 적용 상태와 남은 구분

Drone에는 비교 시험에서 수신율 개선 가능성을 보인 10ms scan interval/window와 요청 시 출력하는 `radio_diag` 카운터를 적용했습니다. 이는 잠정 완화 설정이며, 마지막 반복에서도 누락이 있었으므로 해결 완료로 보지 않습니다. Reader는 원래의 100ms 스캔/200ms 질의 광고로 복원했습니다. GUI의 수동 상태 확인으로 카운터를 볼 수 있으며 대기 중 주기 로그는 추가하지 않았습니다.

72회 전체 측정에서 Drone 질의 수신은 49회, 최종 FRIEND는 37회였습니다. 실패 35회 중 23회는 Drone RX_CHALLENGE가 없었고, 12회는 질의 인증과 응답 광고 시작 이후 Reader가 응답을 받지 못했습니다.

기본 광고 채널에서 질의를 발견하지 못한 것인지, 보조 채널의 전체 데이터를 받지 못한 것인지는 패킷 스니퍼가 있어야 확정할 수 있습니다. 남는 응답 손실은 Reader 수신 카운터를 같은 방식으로 추가하거나 양쪽 무선 패킷을 캡처해 다음 단계에서 구분할 수 있습니다.

펌웨어 호스트 검사 5개(프로토콜 독립 HMAC 벡터, 실제 Reader/Drone 상태 전이, BLE 프레이밍 경계 및 변조)를 ASan/UBSan 환경에서 통과했습니다. 최종 NU40 보드 빌드와 업로드도 완료했습니다.
