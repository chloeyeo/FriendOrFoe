# firmware/ — the gadgets (Arduino C/C++), owner: stream 2 (Ihan)

The IFF protocol FOF-1 runs on the gadgets, not on the phone. Nothing here is compiled by Gradle; the Arduino
toolchain builds it and the `selftest` sketch on the board is the test suite.

```
iff/        the fof1 Arduino library — src/fof1.h (API, wire layouts, MAC inputs), src/fof1.cpp (skeleton: every
            function returns FOF1_ERR_NOT_IMPLEMENTED until stream 2 fills it in), library.properties (name=fof1)
selftest/   selftest.ino replays vectors.h (generated by eval/gen_vectors.py) and prints PASS/FAIL per vector
reader/     the observer-side gadget: USB CDC serial to the phone (newline JSON), radio challenge, verify, report
drone/      the drone-side gadget: answers only authenticated challenges; attack modes HONEST/REPLAY/RELAY/LATE/SILENT/IMPOSTOR
```

## Build

**Arduino IDE 2.x**

1. Install the board package for the gadget's MCU (Boards Manager). ESP32-S3 / RP2040 / SAMD boards have native
   USB CDC (the `Serial` object *is* the USB port); classic AVR boards go through a CP210x/CH34x bridge, which the
   phone's `usb-serial-for-android` also drives.
2. Library Manager: **ArduinoJson** (7.x) and **Crypto** by Rhys Weatherley (rweather; gives `SHA256` and
   `HMAC`). On ESP32 you may use the core's built-in mbedtls instead of Crypto (`mbedtls_md_hmac`).
3. Make the `fof1` library visible: copy or symlink `firmware/iff` to `<Arduino sketchbook>/libraries/fof1`
   (Windows: `mklink /D "%USERPROFILE%\Documents\Arduino\libraries\fof1" "C:\...\FriendOrFoe\firmware\iff"`).
4. Open `firmware/selftest/selftest.ino`, pick the board and port, Upload, open the Serial Monitor at 115200.

**arduino-cli**

```
arduino-cli core install esp32:esp32            # or rp2040:rp2040, arduino:samd, ... whatever the gadget is
arduino-cli lib install ArduinoJson Crypto
arduino-cli compile --fqbn esp32:esp32:esp32s3 --library firmware/iff firmware/selftest
arduino-cli upload  --fqbn esp32:esp32:esp32s3 -p COM5 firmware/selftest
arduino-cli monitor -p COM5 -c baudrate=115200
```

Expected output once `fof1.cpp` is implemented: one `PASS <name>` line per vector and `8/8 PASS`. Today (skeleton)
every line is `FAIL <name> at day_of (...)` by design.

## Board notes (open question #1 in README section 7 — decide before H1, write it into docs/GADGET_LINK.md)

- Native-USB boards enumerate as CDC ACM with the vendor's VID/PID (Espressif 303A:xxxx, Raspberry Pi 2E8A:xxxx,
  Arduino 2341:xxxx); `usb-serial-for-android`'s default prober knows the common ones, otherwise add a `ProbeTable`.
- Radio: anything with a packet API and an RSSI readout (LoRa SX127x/SX126x, nRF24L01+, ESP-NOW between two ESP32s).
  The response is 37 bytes, the challenge 31 bytes; one packet each.
- Nonces must come from a hardware RNG (`esp_random()`, the RP2040 ROSC, `analogRead` noise is not acceptable).
- The pre-placed master key lives in NVS/Preferences or EEPROM, never in the sketch source; the TEST key in the
  sketches equals the one in `eval/gen_vectors.py` and must be replaced before the demo.
- Timing: the reader measures `responseMs` from the end of its transmission to the start of the reply; the phone
  independently measures the USB round trip. Both are compared with the 2.5 s budget.

## The USB serial contract

The phone <-> reader line protocol (115200 8N1, one JSON object per line) is specified in `docs/GADGET_LINK.md`
(summary in README "Gadget link over USB"). `laptop/gadget_cli.py` sends the same lines from a laptop so the whole
link can be exercised on the bench before the phone exists: `python laptop/gadget_cli.py --port COM5 status`.
