# Roadmap: FriendOrFoe

## Overview

**Team mode (added 2026-10-10 afternoon):** three developers now work in parallel — Chloe (@chloeyeo) on video detection, app shell and integration; Ihan (@angmusae2015) on the challenge-response (`:iff`, the USB gadget link, the responder fallback logic, PROTOCOL.md); Jongho (@ujon) on the UI frontend and the laptop dashboard. Phase 1 (skeleton, contracts, Gradle wiring) lands first; Phases 2, 3 and 4 then run concurrently as the three streams; Phase 5 is the integration at the H10 checkpoint; Phases 6 and 7 are shared. The signal is expected from the team's own gadgets over USB (`UsbGadgetSignalSource`), with the phone-B QR path as the fallback simulator (`OpticalQrSignalSource`). README.md is the team-facing version of this roadmap, with the module map, ownership and the branch/PR workflow.

FriendOrFoe is built in one 20-hour serial hackathon session by one developer, and the seven phases are the user's hour-plan milestones in order (H0–1, H1–4, H4–7, H7–10, H10–12, H14–17, H17–20; H12–14 is sleep, not a phase). The journey: Phase 1 proves the offline ClikaRT license, puts the model on the phone and the laptop `serve --offline` on the LAN, and lays the `Detector` seam and the `:iff` skeleton; Phase 2 puts live, on-device boxes on a person and the demo drone target (the first thing a judge could see) and decides the demo target; Phase 3 writes the whole FOF-1 protocol as a pure-Kotlin module with tests and JSON vectors, so every verdict is proven on the laptop before any phone wiring; Phase 4 turns phone B into the friendly drone (authenticated listener, QR answer, six attack buttons, hotspot host) and gives the judges a laptop dashboard and a scrcpy mirror; Phase 5 wires tap → challenge → in-box QR decode → ring with reason plus the physical-layer checks, which is the working end-to-end prototype; Phase 6 measures (eval table, on-device numbers), hardens (three airplane-mode run-throughs, backup video) and documents (README); Phase 7 writes PROTOCOL.md, the pitch and the Q&A card and makes the final push.

**Priority: working prototype ASAP.** Within every phase the success criteria are ordered so the runnable increment comes first and polish last; when a phase runs over its time box, the later criteria are the ones that slip or get cut, never the first one.

**Hard checkpoint at H4 (end of Phase 2):** if `ClikaRtDetector` does not run on the phone (license, model load, or latency far below 1 fps), flip the one config value in `Detectors.create` to `HttpDetector` against `clikart-cli serve --offline` on the hotspot LAN and move on — nothing above the `Detector` interface changes. PITFALLS.md #44 warns that an `HttpDetector` demo weakens the SC1 claim ("app built with ClikaRT") and puts the laptop on the critical path, so the switch is the way to keep building Phases 3–5 on schedule, not the demo plan: the Phase 6 buffer re-runs the five-step on-device checklist (license code name → model files and path → RGBA stride/channel dump compared with the CLI → label ids → threshold) before the HTTP path is accepted for the live demo, and the pitch must then say the phone path is the product. **"P1 green" gates at H10 and H14:** no differentiator (Impostor, Relay/position gate, PROTOCOL.md, eval, audio alert, OWLv2) is started unless the table-stakes increment of the current phase is demonstrably working on the devices.

**Cut order if behind (user's order, fixed):** DET-08 audio alert → DET-09 OWLv2 option → IFF-06/RSP-07 Relay button + position gate → EVL-01/02 eval set and table → PHY-02 signal-strength gate. Research (FEATURES.md) recommends cutting the JDG-02/JDG-03 laptop dashboard before all of these, and keeping Relay above the eval table because "resist MITM" is in the T1-04 wording; the user chose to keep the dashboard on 2026-10-10, so JDG-02/03 stay in v1 until the user cuts them. **Conditional (PIT-04):** if COCO cannot see the demo target at H4, change the prop first (printed A3 drone photo or a tablet with phone B at its centre — PITFALLS.md #16); only if no prop works is DET-09 promoted into the critical path (insert it as Phase 2.1) and EVL-01/02 cut first — and OWLv2 on the phone must be benched before it is relied on (≈10 s per frame on the 12-thread laptop CPU, 593 MB fp32 weights; PITFALLS.md #18).

**Ongoing in every phase:** push to GitHub at the end of the phase (PIT-07); never commit the license, keys, `local.properties` or model weights (SEC-01); never log key bytes, the license text or full nonces (SEC-03 is audited in Phase 5 but applies from Phase 1); demo with the same debug-signed build throughout (a new signing key changes `ANDROID_ID`, which the ClikaRT license binds to — PITFALLS.md #8).

Coverage: 54 v1 requirements (REQUIREMENTS.md's earlier figure of 59 was a miscount), each mapped to exactly one phase. Research folded in: FEATURES.md, ARCHITECTURE.md, STACK.md and PITFALLS.md including their 2026-10-10 verification notes; research/SUMMARY.md did not exist when this roadmap was written — planners should read it when it exists. Where the research files disagree (CameraX 1.4.1 vs 1.6.2, `:iff` JVM target 11 vs 17, kotlinx-serialization 1.9.0 vs `org.json` for test JSON, port numbers, FOF-1 challenge key), the phase flags name the conflict and the phase in which it must be decided.

### Phase 3: IFF protocol module, tests first
**Goal**: The complete FOF-1 protocol exists as a pure-Kotlin JVM module with deterministic tests and committed JSON vectors, so every verdict — FRIEND, replayed nonce, bad tag, position mismatch, no response, and the physical-layer reasons late response / signal mismatch / optical mismatch — is proven on the laptop before any phone wiring.
**Depends on**: Phase 1 (the `:iff` skeleton); independent of Phase 2, so it is unblocked even if Phase 2 runs to the H4 checkpoint
**Time box**: H4–7
**Requirements**: IFF-01, IFF-02, IFF-03, IFF-04, IFF-05, IFF-06, IFF-08, SEC-04
**Success Criteria** (what must be TRUE):
  1. `./gradlew :iff:test` is green on the laptop with no device: the fixed binary codecs round-trip with exact lengths (challenge `{v, nonce16, t, challengerId, cmac8}` = 31 B, response `{v, droneId, nonce8, posQ, tag16}` = 37 B), keys derive master → day key (YYYYMMDD) → per-drone key, every MAC is computed over the byte layout and never over JSON text, and a response computed with a wrong key yields `FOE · bad tag`.
  2. The verifier runs its checks in the fixed order — read inside the box → nonce issued, unused and fresh → tag recomputes with the drone key for today ±1 → position gate — and returns the first failing reason; the nonce ledger tracks issued → outstanding → consumed with one outstanding challenge per box and a 10 s age limit; any nonce reuse yields `FOE · replayed nonce`; a 10 s timeout yields `UNKNOWN · no response` and silence can never yield FRIEND; yesterday, today and tomorrow day keys are all accepted.
  3. JSON test vectors committed under `iff/src/test/resources` cover FRIEND, replayed nonce, bad tag, position mismatch and no response (plus late response, signal mismatch and optical mismatch), generated by an independent script rather than by the code under test; a vector test replays every one of them through the verifier and matches, and a deliberately flipped byte fails, so any other responder implementation can be checked against them.
  4. The position gate is a pure function with tests: it accepts a claimed position only within R_max 3 km and either within 30 m (near-field, same room) or within ±20° bearing/elevation of the box cone computed from the configured observer heading, camera HFOV and box position; a position 5 km away yields `FOE · position mismatch`, and the exact configured demo coordinates for Honest and Relay are among the tests.
  5. The physical-layer gates exist as pure functions with tests — round-trip timing against a 2.5 s budget → `FOE · late response`; RSSI floor (−70 dBm) and RSSI-derived range against the near-field claim → `FOE · signal mismatch`, with an explicit "n/a → skip unless strict" input; optical persistence (two consecutive frames) and pixel-size plausibility → `FOE · optical mismatch` — and nonces come from `SecureRandom` with constant-time tag comparison. (PHY-01..03 themselves are verified in Phase 5 when wired to the camera and Wi-Fi.)

**Research flags** (ARCHITECTURE.md, PITFALLS.md #N, STACK.md):
- Key hierarchy — settle at the start of this phase and record in PROJECT.md Key Decisions: ARCHITECTURE.md's verified version keeps PROJECT.md's FOF-1 derivation (challenge `cmac` under the day key; response tag recomputed with the per-drone key for today ±1) and flags for the user's confirmation that a responder holding the day key can derive every drone's key for that day, so "a captured drone leaks only its own key" does not hold unless the challenge MAC moves to a derived `chKey = HMAC(dayKey, "FOF-chal")`. PITFALLS #27 adds: derive the day from the challenge's `t` in UTC on both sides (midnight UTC is 09:00 KST — a plausible demo hour), have the responder reject `|t − now| > 120 s`, set both phones to automatic time while still online, and put a `skewSeconds` field in the vectors.
- Canonical MAC inputs (#24, anti-pattern 6): fixed-width big-endian fields only — `"C" ‖ v(u8) ‖ nonce(16) ‖ t ‖ challengerId(u16)` and `"R" ‖ v ‖ nonce(16) ‖ t ‖ challengerId ‖ droneId(u16) ‖ latQ(i32) ‖ lonQ(i32) ‖ altQ(i16)`; decide the width of `t` once (ARCHITECTURE u32 seconds → 31 B; PITFALLS u64); quantise with floor, not truncation (Kotlin `toInt()` truncates toward zero, Python `//` floors — include a southern-hemisphere coordinate). Vectors come from a ~40-line Python generator (`hmac`, `hashlib`, `struct`) in `eval/`, consumed by the Kotlin tests, never regenerated from Kotlin.
- Byte budget: challenge 31 B → base64url 42 chars on the HTTP leg; response 37 raw bytes fit QR version 3-M (42 B) in byte mode — base64url text (54 mixed-case chars) does not fit version 3. Add a test that the encoded response fits QR version ≤ 4 (ZXing `Encoder`, test-only dependency, #21).
- Nonces and clocks (#26, #28): `java.security.SecureRandom()` default (the "Crypto" provider is gone on API 28+), injected as a function so tests are deterministic; key the ledger by hex string (a `ByteArray` map key never matches); inject a `Clock` with `epochSeconds()` and `monotonicMillis()` — never `System.currentTimeMillis()` inside `:iff`; prune entries older than 60 s on insert; mark a nonce used on the first successful verification; `challengerId` in both MAC inputs; ledger entry = nonce → (boxId, issuedAt, used); re-tapping a box cancels its previous entry; keep used nonces ~10 min so a replay reads `replayed nonce`, not `unknown nonce`; "expired" is its own reason.
- Constant-time compare (#25): own `ctEquals` or `MessageDigest.isEqual`, over the full 16-byte tag.
- Demo coordinates (#30): PITFALLS proposes observer `lat0, lon0, alt0, heading0`, Honest = 100 m along `heading0` (alt0 + 10 m), Relay = 100 m at `heading0 + 90°` or 5 km away, so the cone is actually exercised; PROJECT.md's near-field rule (< 30 m passes without bearing) would skip the cone for two phones in one room — decide which the demo shows, unit-test the cone with the exact configured coordinates, and plan a HUD line with expected / measured / delta for Phase 5.
- No Android in `:iff` (#29): `java.util.Base64`, `javax.crypto.Mac`, `ByteBuffer`; JSON only in tests (`org.json` as `testImplementation`, or kotlinx-serialization 1.9.0 with the 2.2.10 plugin per STACK); never `returnDefaultValues = true`; JUnit 4 (avoids Gradle 9 JUnit-Platform wiring). `:iff` main stays dependency-free so the jar can later check a Python/ESP32 responder.
- Logging policy applies here too: tests and helpers print 8-hex nonce prefixes only, never key bytes (SEC-03 is audited in Phase 5).

### Phase 5: Observer integration
**Goal**: The working end-to-end prototype: tap a drone box on phone A, phone B answers with the QR, phone A reads it only inside the locked box and shows a green ring or a red ring with the reason within seconds, with the physical-layer checks, settings, event log, dashboard posting and chime — the exit criterion for H12.

**Time box**: H10–12

**Success Criteria** (what must be TRUE):
  1. The Honest path runs on two phones in airplane mode: tapping the `drone · ?` box sends exactly one authenticated challenge over the hotspot (2 s connect timeout; nothing is transmitted until the tap), draws a 10 s countdown on the box, phone B's QR is decoded only inside the locked box (crop with 10 % margin, ML Kit bundled, QR_CODE only, raw bytes, ≥ 5 fps during the window), and the ring turns green `FRIEND · RQ-07` within about a second of the QR appearing, with the measured round-trip time; a QR shown elsewhere in the frame is ignored.

**Research flags** (FEATURES.md, ARCHITECTURE.md, STACK.md, PITFALLS.md #N):
- ML Kit (anti-pattern 7, #22): only the bundled `com.google.mlkit:barcode-scanning:17.3.0` works offline (the unbundled Play-services artifact downloads its model and "requests before the download has completed produce no results"); restrict to `FORMAT_QR_CODE`; pass an executor so callbacks stay off the main thread; use `Barcode.getRawBytes()` (may return null — treat as no read); warm the scanner up at start (the first `process()` is slow). One-line fallback if ML Kit returns nothing in airplane mode: ZXing `QRCodeReader` on the same crop (STACK).
- Decode cadence and attribution (#22, pattern 3): while a track is CHALLENGED decode on every camera frame (not at the 1 fps detection tick) with detection paused; crop the last known box expanded ~25 % and accept a `Barcode.boundingBox` only if it lies inside the unexpanded box; the decoded nonce prefix must equal the outstanding nonce for that boxId; re-associate boxes between ticks by IoU > 0.3 and keep the last box for 5 s after loss; the tracker coasts a CHALLENGED track for the full 10 s.
- Readability distance (#14, #20): ML Kit needs ≥ 2 px per module; at 1920×1080 a phone-sized QR decodes at 0.6 m and is borderline at 1.0 m (estimates, not measured) — demo at ≤ 0.7 m, or take a one-shot full-resolution `ImageCapture` on tap for roughly double the reach. The analysis stream must not be the 640×480 default.
- Never treat an HTTP 200 or a timeout as a verdict (anti-pattern 5, #33): only the optical response verified by `:iff` may produce FRIEND; send the challenge on `Dispatchers.IO` with explicit connect 2 s / read 3 s timeouts and turn a failed POST into `UNKNOWN · unreachable` immediately (tap to retry); the 10 s window → `UNKNOWN · no response`.
- Position HUD (#30, #31): show expected / measured / delta bearing so a mismatch is explainable in seconds; keep the challenged box within the central third of the frame ("centre the target" hint when |cx/W − 0.5| > 0.17); read HFOV from Camera2 characteristics or assume ~70°; ignore elevation beyond a sanity `|Δalt| < 100 m`; widen to ±30° only if the venue rehearsal shows misses, and say so. Bearing for the DET-08 banner comes from the configured heading + HFOV + box position (the same math as the IFF-06 cone), not a live compass (indoors ±10–30°).
- Verdict text carries the number that explains it (UX): `FOE · position mismatch (Δ 87°)`, `UNKNOWN · no response (10 s)`, `FOE · late response (3.1 s)`; verdicts stick to a track until it dies or is re-challenged; each tap issues a fresh nonce and the old one stays "used" so Replay reads `replayed nonce`; prune the ledger > 60 s (#26).
- TTS trap (DET-08): TTS engines may need downloaded voice data and can prompt for a Play Store download under airplane mode — use a bundled OGG via `SoundPool`.
- Phone A network sequence (#34, #40): airplane mode on → Wi-Fi on → join B's hotspot → dot green; answer "stay connected" to the no-internet prompt, disable "switch to mobile data automatically", and `ConnectivityManager.bindProcessToNetwork(wifiNetwork)` as belt and braces. RSSI comes from `WifiManager` connection info for the attached AP only (which is why phone B hosts); verify on the test phone whether reading it needs `ACCESS_FINE_LOCATION` (request it anyway — it also enables the GPS fix). OFFLINE badge: `Settings.Global.AIRPLANE_MODE_ON` plus `NET_CAPABILITY_VALIDATED == false`.
