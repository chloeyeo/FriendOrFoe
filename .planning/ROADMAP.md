# Roadmap: FriendOrFoe

## Overview

**Team mode (2026-10-10 afternoon, revised the same evening for the gadget decisions):** three developers work in parallel — Chloe (@chloeyeo) on video detection, the app shell and integration (lead); Ihan (@angmusae2015) on the challenge-response, stream 2: the FOF-1 protocol in Arduino C/C++ on the team's own gadgets (`firmware/iff` library, `reader`, `drone` and `selftest` sketches), the USB gadget link on the phone (`app/.../signal`), `docs/PROTOCOL.md` and `docs/GADGET_LINK.md`; Jongho (@ujon) on the UI frontend and the laptop dashboard. Phase 1 (skeleton: package stubs, the three contracts, fakes, Gradle and firmware wiring) lands first; Phases 2, 3 and 4 then run **concurrently** as the three streams (Phase 2 = stream 1; Phases 3 and 4 = stream 2, with stream 3 building the overlay and screens against `DemoScenario` and delivering the dashboard inside Phase 4); Phase 5 is the integration at the H10 checkpoint; Phases 6 and 7 are shared. Integration checkpoints: **H4** live boxes · **H10** end-to-end green ring with the gadget · **H14** three rehearsals + backup video · **H20** submission — GitHub milestones with those names exist and about 30 issues were created from this plan. The signal comes from the team's own gadgets: the reader gadget on the phone's USB OTG port runs the radio challenge-response and the crypto itself and reports verdict + RSSI + response time + nonce as newline JSON (`UsbGadgetSignalSource`); the phone re-checks only (nonce never seen, round-trip budget, RSSI floor, attribution); `FakeSignalSource` is the simulator and the on-stage fallback. There is no second-phone responder and no Kotlin `:iff` module. README.md is the team-facing version of this roadmap, with the module map, the contracts, ownership and the branch/PR workflow.

FriendOrFoe is built in one 20-hour hackathon day, and the seven phases are the hour-plan milestones in order (H0–1, H1–4, H4–7, H7–10, H10–12, H14–17, H17–20; H12–14 is sleep, not a phase). The time boxes are the serial plan; in team mode they are the latest a phase may finish, and the streams start Phases 2, 3 and 4 as soon as Phase 1 lands. The journey: Phase 1 proves the offline ClikaRT license, puts the model on the phone and the laptop `serve --offline` on the LAN, and lays the `Detector` / `SignalSource` / `ObserverUiState` contracts, the `firmware/` skeleton and `laptop/gadget_cli.py`; Phase 2 puts live, on-device boxes on a person and the demo drone target (the first thing a judge could see) and decides the demo target; Phase 3 writes the whole FOF-1 protocol in Arduino C/C++ in `firmware/iff` and proves every verdict with the `selftest` sketch against Python-generated JSON vectors on the bench, before any radio or phone wiring; Phase 4 brings the gadget link up end to end on the bench — the `reader` and `drone` sketches with the six attack modes, exercised from the laptop with `gadget_cli.py` — writes the phone's `UsbGadgetSignalSource` / `GadgetLineCodec` / `ReChecks` / `FakeSignalSource`, and gives the judges the dashboard on 8081 and a scrcpy mirror; Phase 5 wires tap → gadget → re-check → verdict → ring with the settings, event log, dashboard posting and chime, which is the working end-to-end prototype (H10); Phase 6 measures (eval table, on-device numbers), hardens (three airplane-mode run-throughs with the gadget attached, backup video) and documents (README); Phase 7 writes PROTOCOL.md and GADGET_LINK.md, the pitch and the Q&A card and makes the final push.

**Priority: working prototype ASAP.** Within every phase the success criteria are ordered so the runnable increment comes first and polish last; when a phase runs over its time box, the later criteria are the ones that slip or get cut, never the first one.

**Hard checkpoint at H4 (end of Phase 2):** if `ClikaRtDetector` does not run on the phone (license, model load, or latency far below 1 fps), flip the one config value in `Detectors.create` to `HttpDetector` against `clikart-cli serve --offline` on the laptop LAN and move on — nothing above the `Detector` interface changes. PITFALLS.md #44 warns that an `HttpDetector` demo weakens the SC1 claim ("app built with ClikaRT") and puts the laptop on the critical path, so the switch is the way to keep building Phase 5 on schedule, not the demo plan: the Phase 6 buffer re-runs the five-step on-device checklist (license code name → model files and path → RGBA stride/channel dump compared with the CLI → label ids → threshold) before the HTTP path is accepted for the live demo, and the pitch must then say the phone path is the product. **"P1 green" gates at H10 and H14:** no differentiator (Impostor, Relay/position gate, PROTOCOL.md, eval, audio alert, OWLv2) is started unless the table-stakes increment of the current phase is demonstrably working on the devices.

**Cut order if behind (user's order, fixed):** DET-08 audio alert → DET-09 OWLv2 option → IFF-06 position gate together with FW-06's Relay mode → EVL-01/02 eval set and table → PHY-02 RSSI gate. Never cut: live boxes, the green/red ring with a reason, the offline run, the `selftest` vectors (FW-04) and `FakeSignalSource` (SIG-04 — the on-stage fallback if the gadget misbehaves). Research (FEATURES.md) recommended cutting the JDG-02/JDG-03 laptop dashboard before all of these; the user kept it on 2026-10-10 and it is now the UI stream's work off the critical path. **Conditional (PIT-04):** if COCO cannot see the demo target at H4, change the prop first (printed A3 drone photo, a tablet showing the picture, or a toy — PITFALLS.md #16); only if no prop works is DET-09 promoted into the critical path (insert it as Phase 2.1) and EVL-01/02 cut first — and OWLv2 on the phone must be benched before it is relied on (≈10 s per frame on the 12-thread laptop CPU, 593 MB fp32 weights; PITFALLS.md #18).

**Ongoing in every phase:** push to GitHub at the end of the phase (PIT-07); never commit the license, keys, `secrets.h`, `local.properties` or model weights (SEC-01); never log key bytes, the license text or full nonces (SEC-03 is audited in Phase 5 but applies from Phase 1, on the gadgets' serial consoles too); demo with the same debug-signed build throughout (a new signing key changes `ANDROID_ID`, which the ClikaRT license binds to — PITFALLS.md #8).

Coverage: 51 v1 requirements (REQUIREMENTS.md revised 2026-10-10: RSP-01..13, OBS-03 and PHY-03 removed, IFF-05 folded into FW-04, FW-01..07 and SIG-01..04 added), each mapped to exactly one phase. Research folded in: FEATURES.md, ARCHITECTURE.md, STACK.md, PITFALLS.md and research/SUMMARY.md. The research predates the gadget decision: its findings about the optical answer, the barcode decode, the second phone and that phone hosting the hotspot no longer apply and are dropped from the flags below; its findings on the license, model push, RGBA stride, labelId map, prop test, APK size, cleartext and the LAN still hold (the LAN now serves the laptop dashboard and the HttpDetector contingency only). Where the research files disagree (CameraX 1.4.1 vs 1.6.2, port numbers), the phase flags name the conflict and the phase in which it must be decided; the dashboard port is fixed at 8081.

- Offline license is the gate for Phase 2 (#1): an online `CLIKA1-…` credential fails with `LICENSE_SERVER_UNREACHABLE` the moment the network is gone, and `--version`/`list` prove nothing. - License kind (CLIKA onboarding deck, read 2026-10-10): ClikaRT licenses come in two kinds — an **Online key** needs a route to the Platform at run time and fails with `PHONE_HOME_STALLED` / `LICENSE_SERVER_UNREACHABLE` without network; an **Offline bundle** is verified locally against CLIKA's signature, needs nothing at run time, is shown only once at issue time, and carries an expiry and hardware seats. Confirm the stored credential's kind first (platform.clika.io → Licenses shows "Active, Offline", or `clikart-license-init --force <credential>` prints the kind); if it is Online, issue an Offline bundle (Licenses → + Issue License → Offline) with seats for the laptop and phone A. Only phone A loads the runtime — the gadgets and the laptop dashboard never consume a seat. The Android loader is `Modelverse.load(context, license)` / `ClikaRtAndroid.load(context, license)`; an explicit value wins over the environment.
- Model push (#3): push `<snapshot>/.` (not the directory, or `adb push` nests `dest/dir`) into `/sdcard/Android/data/com.chloeyeo.friendorfoe/files/models/rtdetr_v2_r18vd/`, verify the three files and byte sizes with `adb shell ls -l`; if the push is refused (some Android 13+ builds), `adb push` to `/data/local/tmp` plus `run-as com.chloeyeo.friendorfoe cp` into `filesDir/models`. Load by directory path with `VisionLoadOptions(offline = true, device = "cpu")`. Never `adb uninstall` (it deletes the pushed models) — reinstall with `installDebug` / `adb install -r`.
- Serve binds `127.0.0.1` by default (FEATURES/ARCHITECTURE verification): start it with `--host 0.0.0.0`; multipart field is `image` (not `file`); RT-DETR refuses `prompt`, OWLv2 requires it. `python -I` hides the user-site packages where fastapi/uvicorn/requests/pyserial live — run laptop scripts with plain `python` (STACK).

### Phase 3: IFF protocol on the gadget, vectors first (Ihan)

- Constant-time compare (#25): own `ct_memcmp` over the full 16-byte tag — never `memcmp` for the tag.
- Time on the board: `millis()`/`micros()` with unsigned subtraction for `responseMs`, started when the radio sends the challenge and stopped when the answer frame arrives — that is the number the phone compares with its own round trip (which also includes the USB legs).
